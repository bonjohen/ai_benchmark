Section 3: Search and Verification Strategy

For a model-release claim, verify in this order: first the vendor’s official launch surface, then the vendor’s developer docs/model catalog, then pricing, then changelog/release notes, then any system card or model card. For OpenAI that means product newsroom, models page, pricing, changelog, and system-card pages; for Anthropic it means newsroom, models overview, pricing, release notes, and system cards; for Google it means Gemini models, release notes, pricing, and DeepMind/Google blog; for xAI and Mistral it means news plus docs release notes and model/pricing pages. A release is “confirmed” once at least two of these official surfaces align on model name and availability. 

For a benchmark-performance claim, check the benchmark owner first, not the model vendor. Use the benchmark’s leaderboard or methodology page, then compare against the vendor’s announcement or system card. If the benchmark owner page does not expose the exact run conditions, note that as an uncertainty. For SWE-bench specifically, record whether the claim refers to Verified, Lite, Full, Pro, or another variant, because the public subsets differ and frontier contamination is now a documented concern. For Humanity’s Last Exam, record whether the claim is public-question accuracy, text-only accuracy, or another slice, and note that HLE uses automatic judging and confidence intervals. 

For a pricing change, only treat it as confirmed when the current official pricing page changes or the vendor’s docs explicitly point to a new pricing page. Anthropic’s docs explicitly tell users to check Anthropic’s main pricing page for the most current prices, which is a useful reminder that older docs can lag. Store both the detected HTML snapshot and the timestamp of observation, because price pages often change without a corresponding blog post. 

For a company announcement, confirm from the company newsroom or press-release page first, then from a second official surface such as docs, product page, or investor/press page if available. Only after that should you add Reuters or another reputable outlet for context. For funding, acquisitions, and regulatory stories, prefer Reuters first among secondary sources, then compare with any official press release from the company. TechCrunch is useful as a fast discovery layer but should not be your only confirmation for major claims. 

For a research claim, confirm the paper itself first through arXiv or a publisher page, then use Semantic Scholar to pull metadata, references, citation graph, and similar-paper context. If the paper is described in a company blog, store both the primary paper and the company narrative, but never treat the blog alone as full confirmation of the technical claim. Hugging Face Papers and TechCrunch can surface the story, but arXiv and Semantic Scholar should do the confirming. 

For conflicts, store them as separate claim records instead of choosing one winner too early. Record claim_text, source_type, source_name, page_title, observed_at, and a confidence tier. For example, if a vendor announcement claims top benchmark performance but the benchmark-owner leaderboard shows different conditions, keep both records and mark the vendor claim as “official self-report” and the leaderboard claim as “benchmark-owner report.” This matters especially for arena scores, composite indexes, and public coding benchmarks. 

Recommended search patterns are straightforward and should be automated. For releases: exact model name plus site:vendor-domain, plus “pricing”, “changelog”, “system card”, and “model card”. For benchmarks: exact benchmark name plus “leaderboard”, “methodology”, and model name. For research: exact paper title in quotes, plus author surname if needed, then Semantic Scholar or arXiv lookup. For news: company name plus “Reuters”, then company name plus “newsroom” or “press release”, then date-constrained search around the event. These patterns work well because the official surfaces above are already structured around those nouns and paths.

Section 4: New-Information Discovery Strategy

To discover new model families, poll official model catalogs and changelogs first. OpenAI’s models page, Anthropic’s models overview, Gemini’s models catalog, xAI’s models/pricing page, and Mistral’s changelog all expose model names in forms that are easy to diff. Whenever a new model slug appears, immediately queue follow-up searches for pricing, release notes, system card/model card, and benchmark coverage. 

To discover new benchmark projects, watch three places continuously: benchmark hubs, arXiv, and community-amplified paper feeds. Scale’s benchmark hub, Terminal-Bench’s registry, GAIA’s organization page, and Artificial Analysis methodology pages expose named benchmarks directly; arXiv surfaces new benchmark papers earlier; Hugging Face Papers and forums reveal which ones the community is actually noticing. This combination catches both formal benchmark launches and early benchmark proposals. 

To discover new company pages and new product lines, crawl for path patterns rather than only watching homepages. The most productive path families in this domain are /news, /blog, /research, /docs, /changelog, /release-notes, /pricing, /models, /system-cards, /leaderboard, and /papers. The current official ecosystems from OpenAI, Anthropic, Google, xAI, Mistral, and Cohere already show that these paths are where the durable information lives. When a new lab appears, search immediately for those path families plus GitHub and Hugging Face orgs. 

To discover new papers and research stories before they are widely reported, poll arXiv category recents daily, then enrich through Semantic Scholar and Hugging Face Papers. arXiv gives the earliest signal; Semantic Scholar gives metadata, recommendations, and API access; Hugging Face Papers tells you which items are accumulating attention and code links. This is the cleanest research-discovery loop in the catalog. 

To discover new news stories before they become consensus narratives, use a layered approach: official company pages first, Reuters AI reporting second, TechCrunch AI third, and community sources last. Reuters’ Artificial Intelligencer gives a strong weekly pulse on what matters strategically, while TechCrunch often surfaces startup and product moves earlier. Hugging Face Forums and GitHub issues are useful only as lead generation for later confirmation. 

Searchable sites that are especially valuable for automated or follow-up investigation are Semantic Scholar, arXiv, GitHub, Hugging Face, OpenAI docs/news, Anthropic newsroom/docs, Gemini docs, xAI docs, Mistral docs/news, Reuters search patterns, and TechCrunch AI category archives. Semantic Scholar is strongest for scholarly metadata and related-work confirmation; arXiv is strongest for earliest paper discovery; GitHub is strongest for official repos, releases, and SDK updates; Hugging Face is strongest for model orgs, datasets, papers, and community benchmark surfaces.

Section 5: Practical Intake Guidance

For official newsrooms, docs, release notes, and pricing pages, prefer deterministic polling plus HTML diffing. Poll changelogs every 6–12 hours, product/news pages daily, and pricing pages daily. Store a normalized event record for each detected change with source, title, path, observed timestamp, and extracted model/version names. The highest-value official pages in this catalog are OpenAI’s changelog, Anthropic’s system-card and newsroom pages, Gemini’s release notes, xAI’s release notes, and Mistral’s changelog. 

For benchmark sources, separate “methodology pages” from “leaderboard snapshots.” Methodology pages should be stored as relatively static reference documents and only re-polled weekly unless version history suggests active revision. Leaderboards should be snapshotted daily, or every 6–12 hours if you care about frontier ranking movement. Always store benchmark variant names and evaluation conditions, because a single benchmark family can have multiple incompatible variants. 

For research-discovery sources, use a triage pipeline. arXiv and Hugging Face Papers should feed a “candidate papers” queue, not your authoritative knowledge base. Then enrich candidate papers with Semantic Scholar metadata and, where possible, publisher pages or benchmark pages. Recommended cadence: arXiv every 12 hours, Hugging Face Papers daily, Semantic Scholar on demand or daily refresh for tracked items. Ignore low-signal preprints with no code, no benchmark relevance, and no overlap with tracked labs or topics. 

For news sources, maintain separate confidence tiers. Reuters belongs in the high-confidence secondary tier and can be auto-ingested into “news events” with lighter human review. TechCrunch belongs in a medium-confidence discovery-and-context tier and should trigger confirmation jobs for material claims. Suggested cadence: Reuters every 3–6 hours, TechCrunch every 6–12 hours. Ignore duplicate rewrites of the same company announcement unless they add unique reporting. 

For community sources such as Hugging Face Forums and general GitHub chatter, ingest only minimal metadata by default: title, author, timestamp, tags, and outbound links. These sources are useful for finding new benchmarks, broken eval infra, and early user complaints, but they are noisy. Suggested cadence: daily. Ignore generic support threads, repeated “how do I run this model?” posts, and repo noise unless the thread links to a new benchmark, release, system card, or widely used tool. 

For deduplication, use a composite key rather than URL alone. A practical default is {normalized_title, organization, source_type, canonical_path_or_slug, published_date}. For official model events, also store {model_slug, version_date} when available. This matters because the same event often appears across newsroom posts, changelog entries, docs pages, GitHub releases, and benchmark notes. Keep a separate cross-reference table that links related records rather than merging them blindly. That preserves conflicts and gives the local store a true event graph instead of a flattened list. 

Common low-value pages to ignore are marketing landing pages without dates, duplicate localized docs pages, stale archived leaderboard pages, broken Spaces, and generic overview pages that do not change often. In this catalog, examples include old or archived Open LLM Leaderboard material, localized duplicates of pricing docs, and community mirrors of benchmark pages. Use them as references if needed, but do not spend regular polling budget on them. 

The most practical default cadence for the full pipeline is this: official changelogs every 6–12 hours, official newsrooms daily, benchmark leaderboards daily, research-discovery feeds every 12–24 hours, Reuters every 3–6 hours, TechCrunch every 6–12 hours, and community sources daily. That gives you good freshness without wasting a large amount of bandwidth on slow-moving pages.
